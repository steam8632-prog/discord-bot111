1. Cieľ projektu

Cieľom bolo vytvoriť Cloudflare Worker, ktorý:

prijme signed video URL,

stiahne video z IWARA upstream servera,

sprístupní ho cez vlastný HTTPS URL,

umožní Discordu vytvoriť video preview/embed,

umožní následné prehrávanie videa,

zachová HTTP Range správanie potrebné pre:

seek,

preskakovanie vo videu,

načítavanie iba potrebných častí,

normálne prehrávanie.

Výsledný endpoint má tvar:

https://iwara-proxy.steam8632.workers.dev/video.mp4?url=<ENCODED_IWARA_URL>

2. Najdôležitejší výsledok

Výsledná implementácia bola otestovaná priamo cez Discord.

Overené správanie:

Discord vytvorí video preview.

Video sa začne prehrávať.

Video sa prehrá celé.

Funguje pause/play.

Funguje seek/preskočenie na inú časť videa.

Worker správne spracúva HTTP Range requesty.

Upstream IWARA vracia 206 Partial Content.

Discord preview používa menšie Range requesty.

Samotný Discord media worker používa Range requesty pri prehrávaní.

Worker odpovedá bez chýb.

CPU náklady Workeru sú veľmi malé.

Záver:

Proxy funguje. Nie je potrebné ďalej meniť hlavičky ani Range logiku.

3. Prvý dôležitý problém — URL encoding

Používaný upstream URL obsahuje vlastné query parametre:

https://acheron.iwara.tv/view?hash=...&filename=...&path=...&expires=...


Celý tento URL sa následne používa ako hodnota parametra:

?url=<encoded URL>


Preto musí byť vnútorný URL správne percent-encoded.

Príklad:

encodeURIComponent(upstreamUrl)


Výsledok obsahuje napríklad:

https%3A%2F%2Facheron.iwara.tv%2Fview%3Fhash%3D...


Dôležitý detail:

Pôvodný:

path=2026%2F10%2F01


sa po ďalšom encodingu stane:

path=2026%252F10%252F01


To je správne.

%25 reprezentuje znak %.

5. Prvý typ requestu — Discord preview

Keď bol link vložený do Discordu, Worker dostal:

User-Agent: Mozilla/5.0 (compatible; Discordbot/2.0; +https://discordapp.com)


Worker preto správne identifikoval request ako Discord preview.

Do debug logu sme dostali:

proxyType: discord-preview


a:

upstreamRange: bytes=0-5242879


To znamená:

Discord si pri preview nevypýtal celé 65 MB video.

Vypýtal si iba:

bytes 0-5242879


čiže prvých:

5,242,880 bytes


= 5 MiB.

6. Upstream odpoveď Discord preview

IWARA upstream následne odpovedal:

upstreamContentType: video/mp4
upstreamContentLength: 5242880
upstreamContentRange: bytes 0-5242879/65117390
upstreamStatus: 206


Toto je veľmi dôležitý dôkaz.

Server povedal:

206 Partial Content


a zároveň:

Content-Range: bytes 0-5242879/65117390


Celková veľkosť videa:

65,117,390 bytes


Preview teda dostal iba prvú časť videa.

To je správne správanie.

7. Prečo bolo dôležité zachovať Range

Jedna z najdôležitejších vecí, ktoré sme počas debugovania zistili:

Nesmieme zmeniť proxy na jednoduché fetch(url) + vrátenie celého body bez zachovania Range requestov.

Video prehrávače a Discord media worker očakávajú HTTP Range podporu.

Bez nej môžu vzniknúť problémy:

video sa nezačne správne prehrávať,

seek nebude fungovať,

prehrávač bude musieť sťahovať celý súbor,

Discord preview môže zlyhať,

prehrávanie môže byť neefektívne.

Preto Worker musí prenášať Range požiadavky smerom na upstream.

8. Druhý typ requestu — samotné prehrávanie

Neskôr sme sledovali request zo strany Discord media worker.

Trace ukázal:

cf-worker: discordapp.net


a:

x-discord-caller: media-worker


Zároveň:

range: bytes=0-


Worker teda dostal požiadavku:

Range: bytes=0-


Upstream odpovedal:

206 Partial Content


s:

Content-Range: bytes 0-93219345/93219346


pri inom testovanom videu.

To znamenalo, že celý súbor bol reprezentovaný ako Range response.

9. Najdôležitejší praktický test

Namiesto ďalšieho náhodného menenia hlavičiek sme urobili reálny end-to-end test cez Discord.

Test nebol iba:

curl → Worker → IWARA


ale:

Discord
   ↓
Discord preview/media worker
   ↓
Cloudflare Worker
   ↓
IWARA


To bolo podstatné.

Pretože samotný HTTP test ešte nedokazuje, že Discord bude video schopný prehrávať.

10. Výsledok end-to-end testu

Pri reálnom prehrávaní bolo potvrdené:

video sa prehráva,

video sa prehralo až do konca,

pause funguje,

play funguje,

seek funguje,

preskočenie na inú pozíciu funguje,

Discord si vie vyžiadať potrebné dáta,

Worker ich vie poslať,

upstream dáta sú správne typu video/mp4.

Toto je definitívny dôkaz, že proxy cesta funguje.

11. Dôležitá chyba v debugovaní, ktorú sme pochopili

Cloudflare Trace môže zobrazovať:

outcome: canceled


To automaticky neznamená:

„video/proxy nefunguje“.

Pri HTTP streaming/media requestoch môže klient request ukončiť alebo zmeniť ešte pred úplným dokončením.

Preto treba pozerať na celý kontext.

V jednom z testov sme mali:

upstreamStatus: 206


a zároveň:

outcome: canceled


Neskôr reálne prehrávanie videa fungovalo.

Preto:

canceled v Trace sme nebrali izolovane ako dôkaz chyby.

12. Ďalší dôležitý poznatok — Discord robí viac requestov

Pri vložení jedného linku do Discordu sme videli dva veľmi podobné requesty.

Oba boli:

User-Agent: Discordbot/2.0


Oba používali:

proxyType: discord-preview


a oba si vypýtali:

bytes=0-5242879


To nie je dôvod na opravu Workeru.

Discord môže preview request zopakovať.

Preto Worker musí byť idempotentný:

rovnaký request → rovnaká správna odpoveď.

13. Čo sa ukázalo ako zbytočné

Po tom, čo bolo potvrdené správne Range správanie, už nemalo zmysel naslepo meniť:

User-Agent,

Accept,

Accept-Encoding,

Referer,

ďalšie HTTP hlavičky,

status code,

Range mechanizmus.

Takéto zmeny by mohli rozbiť už fungujúcu implementáciu.

Princíp:

Ak reálny klient funguje end-to-end, neoptimalizovať hypotetický problém, ktorý sa v praxi neprejavuje.

17. Čo by sa dalo neskôr vylepšiť

Po funkčnej stránke už nie je potrebné nič meniť.

Ak by sa niekedy riešila bezpečnosť logov, bolo by možné maskovať signed URL.

Napríklad namiesto:

https://acheron.iwara.tv/view?hash=...&expires=...


logovať iba:

targetHost: acheron.iwara.tv


a prípadne:

filename: example.mp4


Citlivé hodnoty:

hash
expires
signed query parameters


by sa nemuseli zapisovať.

Ale v tejto fáze sme sa rozhodli:

Nič nemeníme. Job done.
